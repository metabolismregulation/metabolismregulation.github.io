The human-like layout tool lays out SBGN Process Description maps in yEd GraphML the way a curator draws them: story first, then blocks, straight arcs, compact complexes. It is not a program with a layout engine. It is the Claude skill sbgn-human-like-layout: written rules that Claude follows, and scripts that each do one fixed job on a map. The story decisions stay with the person. The map builds use the skill. This page shows where the tool stands, how it is built and what comes next.

How it is built

There is no layout engine. Claude reads the rules, the person decides the story, and the scripts do the jobs that are the same on every map. A map build places the blocks with kit.Layout, then the passes clean up: the standardising pass on every Atlas map, the others where they fit (snap to grid for maps drawn in yEd, hub_grid for maps converted from CellDesigner). No script changes content: check.py --input lists every change of a node, label or arc since the input file. The user finishes the map in yEd, and the edits the user makes there are where the rules come from.

ScriptWhat it does
kit.pyOne style (spacing, ports, junctions). Blocks are laid out in their own coordinates, and a build only moves whole blocks and routes the arcs between them.
transfer_layout.pyThe user's layout of one map onto its twin (same node and arc ids), each map keeping its own content.
move_node.pyMoves nodes by whole steps. A bend on a moved node's centre line moves with it, so its arcs stay straight.
standardise.pyRuns four passes in this order, each on the sizes the one before leaves, and keeps nothing check.py finds worse: icon_sizes (state variables and units of information: sizes, places, text), complex_pack (members at fixed margins and gaps, the arrangement and the centre kept), arrow_room (30 px at arrowheads and bends, made by moving a node or its block), newt_ready (compartments Newt keeps as drawn).
lanes.pyTwo processes on one pair of nodes, opposite or parallel, in two lanes 12 px either side of the line between the nodes.
snap_grid.pyNode centres on an 8 px grid, bends on 4 px, points that belong on one line grouped first, so lines become straight.
hub_grid.pyArcs leaving one side of a metabolite hub at regular intervals, processes off neighbouring lines.
arcs.pyArcs at node centres and soft bends.
check.py, sides.pyFaults: overlaps, arcs through nodes or their own metabolite's name, crossings, arcs too close, two antennas broken, bends near arrowheads, pairs not in lanes, icons off the standard, groups yEd redraws, what Newt would still move. Measures: orthogonal and almost straight segments, extent. With --input, content changes.
inspect_graphml.py, stats.pyThe network as a list before a layout is planned, the house style measured.

The order for large maps

Coarse to fine: the decisions with the largest effect first, the cheap local fixes last, so a late fix never undoes an early one. For a map that already has a layout, that layout is kept as the reader's mental map: good blocks stay, crowded ones get room.

StepUnitHow
1. The story: main story, substories, hubsthe mapby hand
2. Blocks laid out on their ownabout 20 processeskit.py
3. Blocks placed, from the hubs outward10 to 30 blocksby hand, placer planned
4. Ports, then routing between blocksarcs between blocksports built, router planned
5. Hubs: ports spread, then flows mergeda hub's arcshub_grid.py, merges by hand
6. Small gridnodes, bendssnap_grid.py
7. Local passesa node, a pair, a complexlanes.py, standardise.py
8. Labelsan arc endrule in SKILL.md
9. Checkthe mapcheck.py

This order is a first path (P1). A path is one order of the same steps, and others are to be timed against it: cleaning first (sizes, spacing, grid, ports, lanes) for a map that already has a layout, the hub first, then outward process by process, and every arc at node centres until the end, with metabolite names cleared last. A path wins when it is fastest without being worse on any count or in the user's judgement in yEd. The terms are defined in the vocabulary.

How the rules grow

Every map the user corrects teaches something. A lesson goes first into notes/lessons.md, with the map, the date and what the user changed. At the end of the session it goes to one of three places: a rule in SKILL.md when it applies across maps, the map's README when it is a choice for that map, or nowhere when a rule already covers it. Suggested on 2026-10-26, to keep the rules from piling up:

  • A lesson improves a rule in place, covers a situation no rule covers yet, or goes to the map's README. Nothing restates, patches or contradicts a rule already there.
  • Each rule in one place, in one or two sentences, marked strict, preference or option, with its scope (maps drawn here, maps converted from CellDesigner). Where it came from stays in lessons.md.
  • A fixed order when rules collide: content unchanged, the user's own geometry, the story, strict rules, preferences, options.
  • A rule about geometry gets a check, and every check runs on the approved examples: a check that flags an approved layout means the rule contradicts the user's taste.
  • The measure is the user's work: how many nodes and arcs the user changes in a version the tool drew. Rules may grow as long as that falls.

Left for later

  • One reader: five readers could drift apart, but none has so far. The definition that matters most, the bounds yEd computes for a group, is already in one place (complex_pack).
  • One pipeline for every pass: the standardising pass already runs four passes in a fixed order. Lanes, snap and hubs stay outside it until the paths above show where they belong.
  • One renderer: ygml.render_svg is a rough preview Claude looks at while it lays out a map. yrender (map project, 598 lines) draws a map as yEd exports it and makes the Atlas images, and this website keeps a copy. Using yrender for the preview too would mean that what Claude checks is what the Atlas shows. For that it has to move into the skill folder, as the skill zip in claude.ai holds only that folder. Kept as it is: the preview is good enough for laying out, and the user judges the result in yEd.
  • The converter's model: the layout tool reads and writes only yEd GraphML. A CellDesigner map goes to GraphML through the converter, is laid out, and goes back through the converter. Laying out the converter's drawing directly would save those two conversions and would let a file without any drawing (BioPAX, SBML without layout) get its first drawing here.
