The human-like layout tool lays out SBGN Process Description maps in yEd GraphML the way a curator draws them: story first, then blocks, straight arcs, compact complexes. It is the Claude skill sbgn-human-like-layout (private repository metabolismregulation/human-like-layout), and the map builds in maps-workbench use it as a submodule. This page shows how it is built today and the architecture suggested for it.

Today

the same job written more than once not a script

There is no layout engine. The story decisions (the anchor, the side each branch enters from, the blocks) are made by the person, and a build script per map writes them down as positions and routes. The tool is what these scripts share: placement helpers, finishing passes and checks. Most of it is generic, but it grew in two repositories, so the same jobs sit in several places.

JobWhere it is written
Read and write yEd GraphMLFive times: ygml.Model, the helpers in complex_pack (used by snap_grid), hub_grid.load, and in the workbench yedit.py and its own ygml.py (same name, other API). yedit and complex_pack both define realizer, box, set_box, shift.
Place nodes, route arcskit.Layout (with the F001 blocks and F001's _style_fixes in the same file), layout.py (its own copy of translate, put, route, fork), and F022-bcaa/kit.py in the workbench, which 40 of the 82 map builds import from the BCAA folder. kit.Layout is used by one map build and two workbench tools.
CheckTwo check.py. The skill's finds groups yEd redraws and almost straight segments, the workbench's finds off-centre ports and bends not smoothed. SKILL.md section 10 sends to the second for two strict rules. Content identity is a snippet in README.md, run by hand.
Renderygml.render_svg (the skill's preview) and the workbench's yrender.py (the Atlas images, copied to this website).
Testrun_all.sh reproduces only F001. The finishing passes were checked on the 22 archive maps, the examples and the Atlas maps, each time by a script written for that session.

The two grids disagree. hub_grid spaces the arcs at a hub 6 px apart through the hub centre, snap_grid puts bends on a 4 px grid. Tried on the F002 eicosanoids advanced layout (v05, a test, nothing saved): the snap moved all 48 hub ports that hub_grid had placed, to 0, 4 or 8 px, and 108 of the map's 270 off-centre ports at metabolite circles. It also sent 12 arcs through nodes, 2 before. Keeping the ports on circles fixed made it worse (orthogonal segments 332 to 274 of 472), and running the hubs after the snap restored only 26 of the 48. Maps drawn in yEd have their ports at the centre and are not touched (one port moved on the 22 archive and 28 Atlas maps).

Suggested architecture

Three small fixes and some housekeeping, no restructuring. The skill gets the full check and the two fixes for what it reports, so a claude.ai chat with the skill has them too. Snap and hubs are for different maps. The F001 scripts move to examples/. The rest stays as it is (blue: what changes).

changed by the plan the same job written more than once, left as it is not a script

What changes

  • Snap and hubs: one rule in SKILL.md, no code. Snap to grid is for maps drawn in yEd, hub_grid for maps converted from CellDesigner, which are not snapped. Done 2026-10-19.
  • check.py: the skill's check gets the two strict rules only the workbench checks today (off-centre ports, bends not smoothed), as preferences for maps drawn in yEd, not strict rules. The workbench's tools/check.py runs it. Done 2026-10-19.
  • arcs.py: centre ports and soft bends, the two fixes for what the check reports, move from F022-bcaa/kit.py into the skill, and the kit calls them. The rest of the kit stays in the workbench: it works on the workbench's yedit, which edits content, and content is not the layout skill's job. Done 2026-10-19: five recent builds give the same files.
  • F001 scripts: layout.py, or_variant.py, make_v7or.py, A_inside_out.py, B_modular.py, the F001 blocks of kit.py and run_all.sh move to examples/F001-glycolysis-v8-v9/. kit.py keeps the generic Layout class. Done 2026-10-19: the same files byte for byte.

The grid

The hubs keep 6 px, the spacing taken from the user's edit of the arachidonate hub. The two passes never meet: the snap is for maps drawn in yEd, whose arcs leave from node centres and have no hubs to space, and hub_grid for maps converted from CellDesigner, which keep their ports on circles and are not snapped. If converted maps are snapped one day, an 8 px hub spacing is the consistent choice, as the snap already puts hub lines 8 px apart.

Left for later

  • One reader: five readers could drift apart, but none has so far. The definition that matters most, the bounds yEd computes for a group, is already in one place (complex_pack).
  • One pipeline in a fixed order: worth it once snap and hubs run in map builds. Today snap runs in none and hubs in three.
  • One renderer: ygml.render_svg is a rough preview Claude looks at while it lays out a map. yrender (workbench, 542 lines) draws a map as yEd exports it and makes the Atlas images, and this website keeps a copy. Using yrender for the preview too would mean that what Claude checks is what the Atlas shows. For that it has to move into the skill folder, as the skill zip in claude.ai holds only that folder. The workbench and this website would then copy it from there. Kept as it is: the preview is good enough for laying out, and the user judges the result in yEd.
  • map-converter's model: map-converter is being rebuilt around a model that holds a map's biology and its drawing apart. The layout tool reads and writes only yEd GraphML. A CellDesigner map goes to GraphML through the converter, is laid out, and goes back through the converter, which works today. Laying out the converter's drawing directly would save those two conversions and would let a file without any drawing (BioPAX, SBML without layout) get its first drawing here. That has to wait until the new model exists. Until then the bridge is the converter's GraphML.

Order of work

  1. check.py with the two preferences. Done.
  2. arcs.py. Five recent map builds give the same files byte for byte. Done.
  3. The F001 scripts to examples/. run_all.sh gives the same files from there. Done.

First suggestion (outdated)

Kept for comparison. Replaced by the plan above (2026-10-19): most of it costs more than it gains today.

One reader and writer of yEd GraphML that every script uses, the skill's and the workbench's. On it, one file of placement helpers for the map builds, and one finishing pipeline that runs the passes in a fixed order. One check that covers layout, the strict rules and the content. The story stays with the person and the map build, as now. What belongs to one map (the F001 blocks, the harmonisation round) moves to examples/. Later, maps from map-converter's model and from files without a drawing (dashed).

the finishing passes, in one place the map every script reads and writes planned

Why one reader

Every script needs the same facts about a yEd file: which realizer is active, where a group's box is, how to move a group with everything in it, where an arc ends. Five readers give five answers that can drift apart. complex_pack already holds the definition of the bounds yEd computes that check.py and snap_grid use, so that part exists. hub_grid keeps its own list only because it was written first. The workbench's yedit.py and ygml.py then import from the skill.

Why a fixed order

Each pass changes what the next one sees. A complex packed after a snap leaves the grid, insets fitted before the packing are stale, and the two grids above undo each other. One pipeline with one order, and one grid both snap and hubs respect, removes these cases for every map at once. A build calls finish(map, snap=True, hubs=True) and nothing else at its end.

What changes

  • yfile.py: one reader and writer, from complex_pack's helpers and ygml.Model. hub_grid, snap_grid, kit and the workbench's yedit use it.
  • build.py: the generic part of kit.Layout and of F022-bcaa/kit.py (node and arc from a template, fit_label), so map builds no longer import from the BCAA folder.
  • finish.py: the passes in one order, the grid decided once. centre_ports and smooth_bends, today in the BCAA kit, become passes.
  • check.py: the two merged, the content identity added, siblings inside groups checked too (SKILL.md section 9: today only top-level nodes are compared).
  • Renderer: yrender only. ygml.render_svg goes.
  • F001 scripts: layout.py, or_variant.py, make_v7or.py, A_inside_out.py, B_modular.py, the blocks of kit.py and run_all.sh move to examples/ as a worked example. or_variant.py and make_v7or.py differ in two lines.

Open questions

Answered in the plan above: the grid, the renderer and map-converter's model.

Order of work

  1. Reference files: every finishing pass on the 22 archive maps, the examples and the 28 Atlas maps, and the 82 map builds run once, kept with their outputs.
  2. yfile.py, with the readers moved onto it one at a time. The files stay as they are.
  3. check.py merged. Its report on the reference maps is the sum of the two today.
  4. build.py, map builds moved from the BCAA kit. The files stay as they are.
  5. finish.py and the grid decision, the one intended change in the files.
  6. F001 scripts to examples/, ygml.render_svg removed.
